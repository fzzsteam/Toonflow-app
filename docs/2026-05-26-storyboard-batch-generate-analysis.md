# 批量分镜生成卡顿与 OOM 风险分析

## 背景

2026-05-26 在本地复现“批量生成分镜图”流程时，观察到以下现象：

- 用户点击批量生成后，页面立即出现明显卡顿。
- 后端接口 `/api/production/storyboard/batchGenerateImage` 很快返回 `200`，但后台任务持续执行。
- 生成过程中服务健康检查偶发出现秒级到十几秒级抖动。
- 在线上环境曾出现 Node.js `Reached heap limit Allocation failed - JavaScript heap out of memory`，进程重启。

本次文档用于整理排查结论，并给出优化建议。

## 本次复现结论

### 1. 卡顿不是单个请求报错，而是整条链路资源叠加

批量分镜生成的实际执行过程是：

1. 前端调用 `/api/production/storyboard/batchGenerateImage`
2. 接口很快返回 `200`
3. 后端按默认并发数 `5`，继续后台分批执行生图任务
4. 前端持续高频调用 `/api/production/storyboard/pollingImage`
5. 一旦轮询拿到结果，服务端同步生成缩略图
6. 页面同时继续刷新任务列表、分镜数据和图片资源

因此页面卡顿不是单点失败，而是并发生图、轮询、缩略图、页面刷新叠加导致。

### 2. 本地监控到的直接证据

#### 任务执行行为

- `batchGenerateImage` 返回很快，说明接口没有等待全部图片生成完成。
- 服务日志中多次出现连续 5 次：
  - `图片模型: wan2.7-image-pro`
  - `开始提交图片任务...`
- 说明这条链路的默认行为是每批 5 个分镜同时提图。

#### 健康检查抖动

本次本地监听 `/api/health` 时，正常响应约为 `1ms` 左右，但在生成过程中出现过明显抖动：

- `14.136s`
- `6.590s`
- `9.044s`

这说明服务虽然没有立即挂掉，但 Node 主进程在高峰时被严重阻塞。

#### 内存峰值

本地 Node 进程 RSS 在这轮批量分镜中出现明显抬升：

- 开始前约 `871MB`
- 高峰约 `1.59GB`

本地因为使用了较大的 Node heap，进程没有立即退出；线上如果 heap 更小，更容易直接触发 OOM。

## 根因分析

### 1. 批量接口默认 5 并发执行

代码位置：

- [src/routes/production/storyboard/batchGenerateImage.ts](../src/routes/production/storyboard/batchGenerateImage.ts)

关键点：

- `concurrentCount` 默认值为 `5`
- 后端按批次 `Promise.all` 执行

这意味着一次批量生成会同时拉起 5 个分镜生图任务，而不是单个顺序执行。

### 2. 参考图在 Node 进程内被转换成 base64

代码位置：

- [src/routes/production/storyboard/batchGenerateImage.ts](../src/routes/production/storyboard/batchGenerateImage.ts)
- [src/utils/oss.ts](../src/utils/oss.ts)

流程如下：

1. 读取参考图文件为 `Buffer`
2. `Buffer` 转为 base64 字符串
3. 再拼成 `data:image/...;base64,...`

如果一个分镜平均引用 3 张参考图，每张图约 `1.5MB - 2MB`，那么在单张图转换时，内存中会同时存在：

- 原始 `Buffer`
- base64 字符串
- Data URL 字符串

这一步会产生明显的内存放大。

### 3. 结果图保存时又经历一轮大对象分配

模型返回结果后，保存图片的过程并不是“直接把文件写到磁盘”，而是通常会经历：

1. 拿到结果图 base64 字符串
2. 去掉 `data:image` 前缀
3. `Buffer.from(base64, "base64")` 解码回二进制
4. 再写盘

因此保存阶段内存中会同时存在：

- 原始结果 base64
- 去头后的 base64
- 解码后的结果 `Buffer`

这使得结果保存瞬间也会出现明显的内存峰值。

### 4. 轮询接口同步生成缩略图

代码位置：

- [src/utils/oss.ts](../src/utils/oss.ts)

缩略图生成会触发 `sharp` 做以下工作：

1. 读取原图
2. 解码图片
3. resize
4. 编码新图片
5. 写入缩略图

这一步除了继续占内存，还会明显吃 CPU，并阻塞 Node 主线程。

### 5. 高频轮询和页面刷新叠加

批量生成过程中，前端会持续请求：

- `/api/production/storyboard/pollingImage`
- `/api/production/getFlowData`
- `/api/task/getTaskApi`
- 缩略图和图片资源 GET 请求

因此高峰期实际是：

- 后台 5 并发生图
- 轮询频繁打过来
- 轮询返回后又同步做缩略图
- 页面同时刷新多个业务数据

这正是页面卡顿和服务抖动的直接原因。

## 粗略资源估算

假设：

- 1 个分镜平均引用 3 张参考图
- 每张参考图 `1.5MB - 2MB`
- 批量并发数 `5`

仅参考图阶段，单张图在转换瞬间大致会同时占用：

- 原始 `Buffer`：`1.5MB - 2MB`
- base64 字符串：约 `2.0MB - 2.7MB`

单张图粗略可按 `3.5MB - 4.7MB` 估算。

则：

- 单分镜 3 张参考图：约 `10.5MB - 14MB+`
- 5 并发：约 `52MB - 70MB+`

再叠加以下因素：

- 结果图保存的 base64 和 `Buffer`
- `sharp` 生成缩略图的中间对象
- 请求对象、轮询返回对象、数据库结果对象
- 大对象尚未被 GC 回收时的重叠

实际运行中，进程额外抬升到几百 MB 是合理现象。本次本地观测到从约 `871MB` 上升到约 `1.59GB`，与该分析方向一致。

## 为什么线上更容易出问题

本地虽然出现明显卡顿，但没有立即崩溃，主要原因是：

- 本地 Node heap 较大
- 本地机器内存相对更宽松

线上如果满足以下任意条件，问题会更容易被放大为 OOM：

- Node heap 只有约 `1GB`
- 容器内存上限更低
- 同时还有其他接口流量
- 同一时段还在跑其他图片任务

因此线上“突然重启”并不是偶然，而是这条链路在资源紧张条件下的自然结果。

## 优化建议

### 一、优先止血

这部分优先级最高，收益也最直接：

1. 降低并发数
   - 将批量分镜默认并发从 `5` 降到 `2`
   - 如果线上仍不稳定，可临时降到 `1`

2. 轮询接口不做同步缩略图
   - `pollingImage` 只返回状态和结果路径
   - 缩略图改为异步后台生成

3. 降低轮询频率
   - 将高频短轮询改为更长间隔
   - 或在无新增结果时做退避

4. 限制单次批量规模
   - 一次最多处理固定数量分镜，避免大批量同时入场

### 二、减少内存放大

1. 参考图不要走 base64
   - 尽量改为传文件路径、临时 URL 或流式读取

2. 结果图不要优先走 base64 落盘
   - 若模型 SDK 支持 URL、Buffer 或流式输出，优先使用

3. 尽量缩短大对象生命周期
   - 结果保存后尽快释放大字符串和大 Buffer

### 三、减少主线程阻塞

1. 缩略图放到后台任务队列
   - 不要在业务接口中同步 `sharp.resize`

2. 将重 CPU 图像处理从主服务进程移出
   - 可以用 worker 或独立任务消费进程

3. 对缩略图做缓存保护
   - 同一张图避免被多个请求重复触发缩略图生成

### 四、调度层优化

1. 批量生成改为真正的任务队列
   - 接口只负责入队
   - worker 负责消费和状态推进

2. 页面改成增量刷新
   - 避免生成过程中频繁全量拉取 `getFlowData`

3. 增加运行时保护
   - 根据内存占用动态降并发
   - 或在高水位时暂停派发新任务

## 建议执行顺序

建议先做最小止血版：

1. 并发数 `5 -> 2`
2. `pollingImage` 去掉同步缩略图
3. 轮询降频

如果这三项上线后效果明显，再继续推进：

4. 参考图/结果图去 base64 化
5. 缩略图后台队列化
6. 批量任务真正队列化

## 最终结论

本次问题的核心，不是单张图片太大，也不是某一个请求单独报错，而是以下三件事同时发生：

- 批量分镜默认 5 并发
- 参考图和结果图在 Node 进程中反复进行 base64 与 `Buffer` 转换
- 轮询接口同步触发缩略图生成

这三者叠加会带来：

- 内存峰值上升
- GC 变重
- CPU 被 `sharp` 和大对象处理占用
- Node 事件循环阻塞
- 页面明显卡顿
- 在线上小内存环境中进一步演化为 OOM 和进程重启

因此，短期需要先止血，长期需要把这条链路从“主进程内大对象同步处理”调整为“低并发 + 异步图像处理 + 更轻的数据传递方式”。
